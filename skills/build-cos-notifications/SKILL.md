# Building COS Notifications

## What a Notification Is

A `Notification` is a `Notification` knowledge graph node (spec §6.2) generated by the LLM when rule conditions are met. It is NOT a push alert — in the prototype it is surfaced on demand via `pnpm notify` or `@bigboss brief me`. Scheduled Lambda delivery is Phase 2.

Every notification must be grounded in at least one `SourceArtifact` chunk. No notification without `sourceNodeIds`.

## Trigger Types (11)

```typescript
type NotificationTriggerType =
  | "upcoming-meeting"          // starts within 60 min
  | "meeting-prep-needed"       // starts within 3h AND no prep query run
  | "unresolved-email-thread"   // >72h old, not resolved, not replied
  | "reply-needed"              // replyNeeded=true AND last message >24h
  | "asana-task-due"            // due within 24h, not completed
  | "asana-task-overdue"        // due date passed, not completed
  | "asana-mention"             // @executive in comment within last 4h
  | "missed-commitment"         // assigned task due past, not completed
  | "calendar-task-conflict"    // task deadline overlaps back-to-back meetings
  | "repeated-topic-priority"   // same topic ≥3 times across sources in 7 days
  | "executive-priority-signal" // LLM-inferred high-stakes topic
```

## Priority Scoring Formula

Every notification gets a `priorityScore` in `[0.0, 1.0]`:

```
score = 0.35 * urgencyScore
      + 0.30 * importanceScore
      + 0.20 * recencyScore
      + 0.15 * execSignalScore

urgencyScore    = timePressureDecay(hoursUntilDeadline)
importanceScore = attendeeRankScore + topicFrequencyScore
recencyScore    = exp(-daysSinceEvent / 7)
execSignalScore = repeatedTopicFrequency normalized to [0, 1]
```

Weights are named constants in `notifications/rules.ts` — never hardcoded inline. Default baseline scores per trigger type: spec §8.4. The formula is parameterized; if you change weights, update the table in the spec.

## Generation Pipeline

```
1. Run trigger rules engine against graph state
   → produces candidate (sourceNodeIds[], triggerType, baselineScore) tuples

2. Score candidates using priority formula
   → discard anything below threshold (default: 0.40)

3. For top-N candidates (default: 10), call LLM via Vercel AI SDK:
   - Retrieve context chunks for each sourceNodeId (RAG topK=8)
   - Prompt: generate Notification fields (title, explanation, suggestedAction,
     confidence) grounded in retrieved chunks
   - Every field must be derivable from retrieved chunks — no hallucination

4. Write Notification nodes to graph.db
   → each with status: "pending"

5. Return sorted list (highest priorityScore first)
```

Wire LangSmith before step 3. `LangSmith.flush()` after step 5.

## Notification Schema Fields

Required fields — do not omit any:

| Field | Type | Rule |
|---|---|---|
| `triggerType` | `NotificationTriggerType` | From rule that fired |
| `priorityScore` | `number` [0,1] | Computed by scoring formula |
| `title` | `string` | One actionable line, ≤100 chars |
| `explanation` | `string` | 2–3 sentences; cite sources |
| `suggestedAction` | `string` | Concrete next step, not vague |
| `confidence` | `number` [0,1] | LLM self-reported |
| `sourceNodeIds` | `string[]` | At least 1; IDs of triggering nodes |
| `generatedAt` | ISO 8601 | |
| `status` | `"pending"` | Always `pending` on creation |

## Notification Lifecycle

```
pending
  → delivered   (surfaced to user in Cursor or Lambda push — Phase 2)
  → dismissed   (user dismisses; suppress same source+trigger for 7 days)
  → snoozed     (user snoozes; set snoozedUntil; re-surface as new notification)
  → acted-on    (user took action; linked to SuggestedResponse or calendar action)
```

Suppress rules:
- Dismissed: same `(sourceNodeId, triggerType)` pair suppressed for 7 days
- Snoozed: re-surface at `snoozedUntil`; create a new `Notification` node (do not reuse the snoozed one)
- Do not generate duplicate notifications for the same triggering condition within a 1-hour window

## Deduplication

Before generating notifications, check for existing `Notification` nodes with:
- Same `triggerType`
- Overlapping `sourceNodeIds`
- `generatedAt` within last 60 minutes
- `status` in `("pending", "delivered")`

If found: skip generation. Return existing notification. Idempotency prevents notification spam.

## What Not to Do

- Do not generate notifications without grounding in `sourceNodeIds`. An `executive-priority-signal` still needs at least one retrieved chunk.
- Do not create `"upcoming-meeting"` notifications for meetings already past (check `endAt > now`).
- Do not include email body text in the LLM prompt for notification generation — use chunk IDs to retrieve relevant excerpts and pass those instead. Full body text is forbidden in LLM context for privacy reasons.
- Do not set `status: "delivered"` in the prototype — delivery is Phase 2. Always write `status: "pending"`.
- Do not implement push notification delivery (Lambda/EventBridge/webhook) in the prototype.
